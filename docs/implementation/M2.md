# M2 — Production-Grade Run Scheduler and Lifecycle Management

## Overview

This document describes the M2 implementation for the TaskFleet project, which introduces a production-grade scheduler and controlled execution lifecycle for AI agent runs. The previous M1 implementation used fire-and-forget execution, where runs were launched immediately without any queue or concurrency management.

M2 replaces this with a proper scheduler service that manages run queuing, concurrent execution, cancellation, and restart recovery.

## 2. Scheduler Service

### Scheduler Architecture

The SchedulerService manages run execution with the following responsibilities:

- **Queue Management**: New runs are enqueued instead of immediately executed
- **Concurrency Control**: Only `MAX_CONCURRENT_RUNS` runs execute simultaneously
- **FIFO Ordering**: Runs are executed in first-in-first-out order
- **Priority Support**: Tasks can have priority (low, medium, high, urgent)
- **Atomic Claiming**: Runs are atomically claimed from the queue using database transactions
- **Failure Handling**: Graceful handling of scheduler failures and orphaned runs

### Configuration

The scheduler is configured via the `MAX_CONCURRENT_RUNS` environment variable:

```bash
# Default: 3 concurrent runs
MAX_CONCURRENT_RUNS=3
```

### Scheduler Service API

```typescript
// Submit a new run to the scheduler
await scheduler.submitRun(runId, taskId, prompt, agentId, priority);

// Cancel a run (queued or running)
await scheduler.cancelRun(runId);

// Process the queue (start next runs when capacity available)
await scheduler.processQueue();

// Shut down the scheduler gracefully
await scheduler.shutdown();
```

### Concurrency Implementation

The scheduler uses atomic database operations to claim runs:

1. Scheduler polls for queued runs
2. When capacity available, it atomically checks if a run is still `queued`
3. If yes, it updates the run status to `running` in a transaction
4. The run is then executed by RunService
5. On completion, the scheduler marks the run as `completed` or `failed`
6. The scheduler then processes the next queued run

### Duplicate Execution Prevention

Duplicate runs are prevented by:

- Checking if a run already exists in any terminal state (completed, failed, cancelled)
- Checking if a run is already in the scheduler queue
- Atomic database transaction that re-checks status before updating

## 3. Cancellation

### Cancellation Endpoint

```http
POST /runs/:runId/cancel
```

### Cancellation Behavior

- **Queued runs**: Immediately removed from the scheduler queue and marked as `cancelled` in the database
- **Running runs**: AbortController signals the agent to stop; database status updated to `cancelled`

### AbortSignal Integration

The existing AbortController mechanism in RunService is enhanced:

```typescript
// In RunService.cancelRun()
cancelRun(runId: string): boolean {
  // First try scheduler (queued runs)
  const schedulerCancelled = this.#scheduler.cancelRun(runId);
  if (schedulerCancelled) return true;
  
  // Then try AbortController (running runs)
  const controller = this.#controllers.get(runId);
  if (controller) {
    controller.abort();  // Signal agent to stop
    return true;
  }
  return false;
}
```

### Child Process Termination

When a running run is cancelled, the child processes (test commands, git operations) are terminated via the AbortSignal:

```typescript
// test-runner.ts already handles AbortSignal
// When signal.abort() is called, test runner resolves with "skipped" status
```

### Git Operation Prevention

After cancellation, additional Git operations are prevented by:

- Checking the run status before performing Git operations
- Aborting any in-progress Git operations
- Marking the run as cancelled so no further Git actions are attempted

### SSE Events

When a run is cancelled, the following SSE event is emitted:

```
event: run.cancelled
data: {"runId":"run-123","taskId":"task-456","type":"run.cancelled","message":"Run run-123 cancelled","percent":100}
```

## 4. Restart Recovery

### Orphaned Run Identification

On application startup, the scheduler identifies orphaned runs:

```typescript
// Find all runs still in "running" state
const runningRuns = await store.listRuns({ status: "running" });
```

### Recovery Policy

- **Running runs**: Marked as `failed` with reason "Interrupted by application restart"
- **Queued runs**: Kept in the queue for the scheduler to pick up
- **Completed/failed/cancelled runs**: Left as-is

### Recovery Implementation

```typescript
async function recoveryOnStartup(store: RunStore, scheduler: SchedulerService) {
  const runningRuns = await store.listRuns({ status: "running" });
  
  for (const run of runningRuns) {
    await store.completeRun(run.id, {
      status: "failed",
      error: {
        code: "INTERRUPTED_BY_RESTART",
        message: "Run was interrupted by application restart",
      },
    });
    // Publish run.failed SSE event
  }
  
  // Process queue to start pending runs
  await scheduler.processQueue();
}
```

### Duplicate Execution Prevention on Restart

- All orphaned runs are marked as failed, preventing them from being re-executed
- The scheduler's duplicate prevention logic ensures no run is executed twice
- Queued runs are recovered and will be executed by the scheduler

## 5. SSE Integration

### New Events

The following events are now supported via the RunEventBus:

| Event Type | Description |
|---|---|
| `run.queued` | Emitted when a run is enqueued in the scheduler |
| `run.started` | Emitted when a run starts execution |
| `run.completed` | Emitted when a run completes successfully |
| `run.failed` | Emitted when a run fails |
| `run.cancelled` | Emitted when a run is cancelled |

### Event Format

```typescript
interface RunEvent {
  id: string;        // Unique event ID
  runId: string;     // Run identifier
  taskId: string;    | Task identifier
  type: RunEventType;
  stage?: string;    // Optional stage (e.g., "agent.started")
  message: string;   | Human-readable message
  percent?: number;  | Progress percentage (0-100)
  data?: unknown;    | Optional additional data
  createdAt: string; | ISO 8601 timestamp
}
```

### Reconnection and Event Replay

- SSE connections include event replay on reconnection
- Persisted events from the database are replayed first
- Live progress events are forwarded after replay
- Heartbeat events (`: ping`) are sent every 15 seconds to keep connections alive

## 13. Troubleshooting

### Common Issues

1. **Runs stuck in "running" state after restart**
   - **Cause**: Scheduler not properly marking orphaned runs
   - **Fix**: Ensure restart recovery runs on startup (added setTimeout in app.ts)

2. **Too many runs executing concurrently**
   - **Cause**: MAX_CONCURRENT_RUNS not set or ignored
   - **Fix**: Set `MAX_CONCURRENT_RUNS` environment variable

3. **Queued runs never execute**
   - **Cause**: Scheduler not processing queue
   - **Fix**: Check that `#pollInterval` is running and `#processQueue` is functional

4. **SSE events not receiving run.cancelled**
   - **Cause**: Event bus not publishing cancellation events
   - **Fix**: Verify `scheduler.cancelRun()` is called and events are published

5. **Duplicate run execution**
   - **Cause**: Race condition in run claiming
   - **Fix**: Ensure atomic database transaction uses proper status check

### Debugging Tips

- Check server logs for scheduler messages
- Use `GET /api/runs` to monitor run statuses
- Use SSE streams (`GET /runs/:runId/events`) to see live events
- Check the `MAX_CONCURRENT_RUNS` environment variable is being read
- Verify Prisma schema migrations have been applied (`npm run db:generate` + `npm run db:push`)
