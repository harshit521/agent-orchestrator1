# M3 — Implement Automated Security Scanning and PR Security Gate

## Overview

This document describes the M3 implementation for the TaskFleet project, which integrates automated security scanning into the run lifecycle. M3 adds Trivy, Gitleaks, and Semgrep scanning of isolated worktrees, security policies (fail-closed vs warn-only), and persistence of scan results.

## 1. Security Scanner

### Existing Infrastructure

TaskFleet already had a `SecurityScanner` class (`apps/api/src/security/scanner.ts`) that supports three security tools:

- **Trivy**: Dependency scanning (`trivy fs <target>`)
- **Gitleaks**: Secret scanning (`gitleaks detect --source <target>`)
- **Semgrep**: Static analysis (`semgrep scan --quiet --json <target>`)

The scanner handles missing tools gracefully by reporting them as `unavailable` instead of failing the entire scan.

### Integration with Run Lifecycle

Security scanning is now triggered as part of the run lifecycle in `#postProcessCodingRun`:

```
Agent execution → Diff generation → Security scan → Policy evaluation → Commit → Push → PR
```

The scan operates on the **isolated worktree** (`taskfleet/<runId>/`) rather than the original repository, ensuring that:

- Each agent's changes are scanned in isolation
- No secrets or vulnerabilities from the original repo are incorrectly flagged
- Scanning is deterministic and reproducible

### Scanner Configuration

Security scanners can be configured via environment variables:

| Variable | Default | Description |
|---|---|---|
| `SECURITY_ENABLED` | `false` | Whether security scanning is enabled |
| `SECURITY_POLICY` | `fail-closed` | Policy: `fail-closed` blocks on blocking findings, `warn-only` reports warnings |
| `SECURITY_SCANNERS` | `gitleaks,semgrep,trivy` | Comma-separated list of scanners to run |
| `SECURITY_SCAN_TIMEOUT_MS` | `120000` | Timeout for each scanner in milliseconds |

### Scanning the Worktree

The scanner runs against the isolated worktree path (e.g., `.taskfleet/worktrees/<runId>/`), not the original repository. This ensures:

- Only the agent's changes are examined
- Context from the original repo doesn't interfere
- Results are specific to the run being evaluated

## 2. Run Security Results

### Persisted Data Model

A new `RunSecurity` model was added to the Prisma schema:

```prisma
model RunSecurity {
  id          String   @id @default(cuid())
  runId       String   @unique
  scannerId   String
  status      String   // passed/failed/unavailable/error
  severity    String   // high/critical/medium/low
  description String
  affectedFile String?
  lineNumber  Int?
  scannedAt   DateTime @default(now())
  error       String?
  run         Run      @relation(fields: [runId], references: [id], onDelete: Cascade)
}
```

### Scan Result Fields

Each security scan result includes:

- **scannerId**: Identifier of the scanner (e.g., "gitleaks", "semgrep", "trivy")
- **status**: `passed`/`failed`/`unavailable`/`error`
- **severity**: Highest severity finding (`high`/`critical`/`medium`/`low`)
- **description**: Human-readable description of the finding
- **affectedFile**: File path where the issue was found (if available)
- **lineNumber**: Line number where the issue occurs (if available)
- **scannedAt**: Timestamp when the scan was performed
- **error**: Error message if the scan failed

### Database Changes

The Prisma schema was updated to add the `RunSecurity` model and a `runSecurity` relation on the `Run` model:

```prisma
model Run {
  // ... existing fields
  runSecurity RunSecurity[] @relation(fields: [id], references: [runId])
}
```

## 3. Security Policy

### Policy Configuration

Two security policies are supported:

| Policy | Behavior |
|---|---|
| **fail-closed** | Blocking findings (high/critical severity) prevent commit, push, and PR creation. The run is marked as failed. |
| **warn-only** | Findings are reported but do not block the lifecycle. The run continues with warnings emitted. |

### Severity Thresholds

Blocked findings are determined by severity:

- **high**: Always blocks (even in `warn-only` mode)
- **critical**: Always blocks
- **medium**: Blocks only in `fail-closed` mode
- **low**: Only reports in `warn-only` mode

### Policy Evaluation

The policy is evaluated in `#evaluateSecurityPolicy()` method:

```typescript
#evaluateSecurityPolicy(securityScan): { block: boolean; reason: string }
```

Returns:
- `block: true`: Security gate blocked, lifecycle halted
- `block: false`: Security gate passed, lifecycle continues

### Detection Categories

Security scanning detects:

1. **Secrets**: API keys, passwords, tokens, SSH keys in code or configuration
2. **Vulnerable Dependencies**: Known vulnerable packages or versions (Trivy)
3. **Code Vulnerabilities**: SQL injection, XSS, and other code patterns (Semgrep)

### Missing Scanner Handling

If a configured scanner is not installed:

- Status: `unavailable`
- Output: `<scanner-name> is not installed.`
- Does not block the lifecycle
- Recorded in database for visibility

### Scan Error Handling

If a scanner encounters an error (not just missing):

- Status: `error`
- Output: Error message
- Recorded in database
- Does not automatically block (depends on policy)

## 4. Run Lifecycle Integration

### Complete Lifecycle Sequence

The enhanced run lifecycle now follows this sequence:

```
1. Agent execution (existing)
2. Diff generation (existing)
3. Security scan (NEW) - Scans isolated worktree
4. Policy evaluation (NEW) - fail-closed/warn-only
5. Commit (existing - only if policy allows)
6. Push (existing - only if commit succeeded)
7. PR creation (existing - only if push succeeded)
```

### Fail-Closed Policy Behavior

When `fail-closed` policy detects a blocking finding:

```text
1. Security scan completes with blocking finding
2. Policy evaluation returns { block: true, reason: "..." }
3. Run is marked as "failed" in database
4. Task status updated to "failed"
5. Security.scan.failed SSE event emitted
6. No commit attempted
7. No push attempted
8. No PR creation attempted
9. Run details show "Security gate failed" with reason
```

### Warn-Only Policy Behavior

When `warn-only` policy detects findings:

```text
1. Security scan completes with findings
2. Policy evaluation returns { block: false, reason: "warnings detected" }
3. Run continues with normal lifecycle
4. Commit proceeds
5. Push proceeds
6. PR creation proceeds
7. Security.scan.completed SSE event emitted
8. Run details show warnings with findings grouped by severity
```

### SSE Events

Two new SSE event types are emitted:

| Event | Trigger | Description |
|---|---|---|
| `security.scan.completed` | Successful clean scan | Scan completed, no blocking findings |
| `security.scan.failed` | Blocking finding detected | Security gate blocked the run |

### Example SSE Stream

```event
event: security.scan.completed
data: {"runId":"run-123","scannerId":"gitleaks","status":"passed","severity":"none","description":"No secrets detected","findings":[]}

event: security.scan.failed
data: {"runId":"run-456","scannerId":"gitleaks","status":"failed","severity":"high","description":"API key detected in code","findings":[{"affectedFile":"src/config.ts","lineNumber":42,"description":"Hardcoded API key"}]}
```

## 6. Testing

### Test Scenarios

The following test scenarios verify M3 functionality:

| Scenario | Expected Result |
|---|---|
| **Known secret detection** | Gitleaks detects hardcoded API key, fail-closed blocks the run |
| **Vulnerable dependency detection** | Trivy detects vulnerable package, blocks the run (fail-closed) |
| **Clean repository** | No findings, lifecycle continues normally |
| **Missing scanner** | Trivy not installed, reported as `unavailable`, lifecycle continues |
| **Scanner execution failure** | Scanner crashes, status `error`, recorded in database |
| **Fail-closed policy** | Blocking finding prevents commit/PR |
| **Warn-only policy** | Findings reported but lifecycle continues |
| **PR blocked when security checks fail** | UI shows "Security gate failed" reason |
| **Successful PR after clean scan** | No findings, PR created successfully |

### Controlled Test Fixtures

Tests use controlled fixtures - never commit real secrets. Test fixtures include:

1. **Secret fixture**: Temporary file with a known API key pattern that Gitleaks can detect
   ```bash
   # Create a temp file with a test secret
   echo "api_key=sk-test-12345" > /tmp/test-secret.txt
   # Run the scanner against it
   npx gitleaks detect --source /tmp/test-secret.txt
   ```

2. **Clean fixture**: Repository with no secrets or vulnerabilities

3. **Vulnerability fixture**: Package.json with a known vulnerable dependency version

### How to Trigger Scans

Security scans are automatically triggered as part of the run lifecycle when:

1. A task is created with `start: true` (default)
2. The agent completes execution and generates a diff
3. The worktree is available (requires `WORKTREES_ENABLED=true`)
4. `SECURITY_ENABLED=true` is set

Manual triggering is not required - the integration is automatic.

### How to Introduce a Test Secret Safely

To test the security scanning without committing real secrets:

1. Create a temporary file with a test secret pattern:
   ```bash
   echo "api_key=sk-test-fake-12345" > /tmp/test-secret.txt
   ```

2. Place the file in the worktree directory (for testing only):
   ```bash
   # This is for testing - don't commit
   cp /tmp/test-secret.txt .taskfleet/worktrees/<runId>/src/config.ts
   ```

3. Run the task and observe the security scan results

4. Clean up after testing:
   ```bash
   rm /tmp/test-secret.txt
   # Remove the test file from worktree
   rm .taskfleet/worktrees/<runId>/src/config.ts
   ```

### How to Verify a Blocked PR

1. Set `SECURITY_ENABLED=true` and `SECURITY_POLICY=fail-closed`
2. Create a task that will produce a secret (e.g., "Configure API keys")
3. Start the task and watch the run detail SSE stream
4. Observe `security.scan.failed` event
5. Check the run detail page shows security gate failed
6. Verify no PR is created (check GitHub repository)
7. Check database: RunSecurity record has `status: "failed"`

### How to Verify a Successful PR

1. Set `SECURITY_ENABLED=true` (with `SECURITY_POLICY=warn-only` or no secrets)
2. Create a task without secrets
3. Start the task and watch the run detail SSE stream
4. Observe `security.scan.completed` event
5. Check the run detail page shows "Security gate: Passed"
6. Verify PR is created on GitHub
7. Check database: RunSecurity record has `status: "passed"`

## Troubleshooting

### Common Issues

1. **Scanners not found**
   - **Symptom**: All scanners report `unavailable`
   - **Fix**: Install the missing scanners or adjust `SECURITY_SCANNERS` to only run available ones

2. **Scan timeout**
   - **Symptom**: Scans take too long or timeout
   - **Fix**: Increase `SECURITY_SCAN_TIMEOUT_MS` or optimize scanner configurations

3. **False positives**
   - **Symptom**: Legitimate code flagged as secrets/vulnerabilities
   - **Fix**: Adjust scanner severity thresholds or add exceptions

4. **Performance impact**
   - **Symptom**: Runs take significantly longer with security scanning
   - **Fix**: Enable only necessary scanners, adjust timeouts, consider `warn-only` policy during development

5. **Database schema mismatch**
   - **Symptom**: Prisma errors related to RunSecurity model
   - **Fix**: Run `prisma generate` and `prisma db push` after schema changes

### Debugging Tips

- Check server logs for scanner output and errors
- Use SSE streams (`GET /runs/:runId/events`) to see live scan events
- Query the database directly: `SELECT * FROM RunSecurity WHERE runId = '<runId>'`
- Enable `NODE_ENV=development` for more detailed error messages
- Check the `SECURITY_ENABLED` flag is set correctly

### Known Limitations

- Scanners operate on the isolated worktree only, not the original repository
- Some Semgrep rules may not be applicable to all codebases
- Trivy requires a database for full vulnerability scanning (offline mode available)
- Gitleaks detection patterns may need tuning for specific codebases
- The `fail-closed` policy may block legitimate development workflows in early phases
